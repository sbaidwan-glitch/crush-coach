# Crush Coach

A task tracker with an AI coach built into every task, for the MuddSub (Harvey Mudd RoboSub) mechanical team. Members claim a task on the robot "Crush", the coach answers questions from the team's own Google Drive and walks them through each stage, leads review the work in the app, and the tracker updates itself as people work.

Owner: Samara Baidwan (mechanical co-lead). Course: E190BO AI-Amplified Prototyping, Fall 2026 final project.

## Stack (course default; don't add frameworks without asking)
- Python 3.13, FastAPI, SQLModel, Alembic migrations, Postgres (psycopg 3)
- Frontend: plain HTML, CSS, JavaScript + htmx, served by FastAPI. No build step, no React (unless Samara asks).
- LLM: called only from the server, only on a user's action, never on page load. Key: `GLASSROOM_API_KEY` (env only).
  - Glassroom is an OpenAI-compatible LiteLLM proxy. Use the pinned `openai` library with `base_url="https://litellm.glassroomai.com/v1"` and `api_key` from `GLASSROOM_API_KEY`.
  - Model comes from `COACH_MODEL` (default `claude-sonnet-5`).
  - All model code lives in `src/llm.py`; no other module imports `openai`.
  - "Tidy my note" (in the Notebook) is a model call on its button: `llm.tidy_note`, with `TIDY_MODEL` (default `claude-haiku-4-5`) and `TIDY_DAILY_LIMIT` (per member per day, default 20). "Suggest specs" (`specs.py`) is one more, on its button, with `SPECS_DAILY_LIMIT` (default 10). Each call is logged to `llm_call` with its cost and its `purpose` (coach, recommend, plan, settle, tidy, specs).
  - Coach settings (env): `COACH_DAILY_LIMIT` (messages per member per day, default 20), `COACH_TIMEZONE` (day boundary, default America/Los_Angeles), `COACH_TIMEOUT_SECONDS` (default 30, per model call; one whole answer is capped at 25 s, see `llm.ANSWER_SECONDS`).
- Google: Drive API v3 (read) + Docs API v1 (append-only write-back, `src/drive_write.py` only), via a service account. `DECISIONS_DOC_ID` is the Crush document (see `docs/crush-document.md`).
- Deploy: Docker on Railway, with PR environments. Pillow is the one imaging library (`photos.py`). Pinned versions in `requirements.txt`; re-pin with `pip freeze` if you add a package.

## Commands
- Use the workspace `.venv` for everything: `.venv/bin/python`, `.venv/bin/pytest`, `.venv/bin/ruff`; never the system Python. Create it with `python3.13 -m venv .venv && .venv/bin/pip install -r requirements.txt`.
- `docker compose up -d`: local Postgres (matches `DATABASE_URL` in `.env.example`)
- `make dev`: run the API on :8000 from `src/`
- `make test`: run tests from `src/`
- `make eval`: score the coach on `evals/coach_questions.yaml` with the real model and the local Drive index (`DATABASE_URL` must point at a synced one; costs money; `ONLY=<id>` or `KIND=<kind>` to run less; `MODEL=<name>` for another model, e.g. `claude-haiku-4-5` or `gemini-3.5-flash-lite`; `RESUME=1` to ask only the questions the last run didn't get to). `make eval RETRIEVAL=1` calls no model and costs nothing: it shows what the coach would be sent per question and whether the facts the answer needs are in it. See "Measuring the coach"
- `make screenshots`: screenshot `/`, `/tasks`, `/tasks/E01`, `/tasks/G01` (a lead was notified), the Notebook (as a page, and the side panel open on its three tabs), a plan answer (`/tasks/M02`) and the Record with work notes and the decision and admin pages (as a member and as a lead) at 375px and 1280px into `.context/screenshots/` (gitignored), against a throwaway SQLite database with the sample tasks and a fake signed-in session. One-time setup: `.venv/bin/pip install -r requirements-dev.txt && .venv/bin/playwright install chromium`
- `make process-shots NAME=home-redesign` (`PAGES="/ /tasks /inbox"` to choose pages; each a path or a name from `PAGES` in `src/scripts/screenshots.py`, default `/` and `/tasks`): runs the screenshots script on the same throwaway SQLite sample data (no real names), light theme, 1280px and 375px, and copies the pictures to `process/YYYY-MM-DD-<NAME>-<page>-<width>.png` (date in `COACH_TIMEZONE`, page = the row name, e.g. `home`, `tasks`). Refuses to overwrite: if any target exists nothing runs. `NAME` is lower-case words and hyphens. Code: `src/scripts/process_shots.py`
- `.venv/bin/ruff check src`: lint
- `cd src && ../.venv/bin/python scripts/drive_search.py "latch"`: search the team shared drive (metadata only); `--type cad|sheets|docs|pdf` filters by file type (the query may be empty with `--type`)
- `cd src && ../.venv/bin/python scripts/drive_list.py "Mechanical/CAD"`: list a Drive folder by path, id or link (names, kinds, modified dates)
- `cd src && ../.venv/bin/python scripts/ask_coach.py "question"`: ask the coach one real question (real model, local Drive index; no server); prints the steps, the answer as it streams, and timing/tokens/cost; `--follow-up "second question"` continues the chat; `--code/--title/--subsystem/--type/--stage` set the task
- `cd src && ../.venv/bin/python -m scripts.sync_drive --full` / `--incremental`: sync the team Drive into the local index (Postgres; the Railway cron job runs `--incremental` every 30 min). `--full --force` re-reads unchanged files. Needs the Google credentials and `DATABASE_URL`; exits 1 if the whole sync fails, 0 if only some files' text couldn't be read
- `cd src && ../.venv/bin/python scripts/index_search.py "lid latch"`: search the local index by hand (the search the coach's retrieval uses); `--type cad|doc|sheet|pdf`, `--limit`, `--full-text`
- `cd src && ../.venv/bin/python scripts/index_stats.py`: counts by kind, chunks, database size, biggest files, what wasn't read; `--noise` shows what to exclude
- `cd src && ../.venv/bin/python scripts/sheet_preview.py "Sheet name"`: how a real sheet is read (which row is the header), read-only, prints real content
- `python -m scripts.sync_drive --full --reindex sheet`: re-read only Sheets (or doc, pdf) after changing how that kind is read. A stopped full sync resumes when run again. See `docs/drive-sync-railway.md` for running it on Railway
- To run the Postgres-only search tests: `TEST_POSTGRES_URL=postgresql://e190bo:localdev@localhost:5432/app make test` (empties the Drive index tables, so use a throwaway database)
- Migrations (run from `src/`; the app also runs `upgrade head` on startup, and a failure there is logged but doesn't stop the app):
  - `cd src && ../.venv/bin/alembic upgrade head`: apply all migrations
  - `cd src && ../.venv/bin/alembic revision --autogenerate -m "describe change"`: create a migration from model changes (needs `DATABASE_URL` pointing at a database already at head; review the generated file before committing)
  - `cd src && ../.venv/bin/alembic downgrade -1`: undo the last migration
  - `cd src && ../.venv/bin/alembic stamp head`: mark a database created before Alembic (by the old `create_all`) as up to date
- `cd src && ../.venv/bin/python -m import_tasks sample_data/tasks.csv`: one-time import of tasks from a CSV into the `Task` table. Safe to re-run: existing task codes are skipped, never overwritten (the `/admin/import` page, not the CLI, can update them). Bad rows are reported and skipped. The sample file is made-up data; never commit a real tracker export.

## Layout
- `src/main.py`: FastAPI app (`uvicorn main:app`)
- `src/`: models, routes, templates, static files, tests
- `src/auth.py`: Google OAuth routes, environment-backed allowlist, signed-session identity, and the reusable route-protection dependency
  - Signed-out visitors (recruiters) get a read-only preview: `/` and `/tasks` render with real progress numbers but `board.preview_tasks` swaps every task's title and owner for made-up text (blurred by `.is-blurred`, not links, Claim disabled), so no real task text or names are in the page source. `/tasks/{code}`, `/record` GETs show `auth.locked_page` (401, a sign-in prompt, nothing read from the database). Every POST and `/admin` still needs `CurrentUser`/`LeadUser`. Use `MaybeUser` only for GET pages that follow this rule; tests override both `auth.require_user` and `auth.optional_user`
- `src/dev_login.py`: **preview environments only.** `GET /dev-login?token=...&as=member|lead` sets the same signed session a real sign-in sets, for made-up `preview.member@example.test` / `preview.lead@example.test` (the lead counts as a lead through `dev_login.role_for`, which `auth.session_user` asks, so `LEAD_EMAILS`/`ALLOWED_EMAILS` are not edited). The route exists only while ALL hold, checked on every request: `DEV_LOGIN=1`, `DEV_LOGIN_TOKEN` non-empty and equal to the `token` (`hmac.compare_digest`), and `RAILWAY_ENVIRONMENT_NAME` set and not `production` (any case; missing = off). Otherwise it answers 404 like an unknown URL, and a session made earlier stops working too. It redirects to `/tasks` so the token isn't left in the address bar, and uvicorn's access log has `token=` blanked (`RedactDevToken`). Never log or echo the token
- `src/home.py` (`/`), `src/board.py` (`/tasks`), `src/templates/`: Home and All tasks (Jinja2 templates; pages are server-rendered). On `/tasks` a signed-in non-lead who owns a task starts on the **Mine** filter (`board.default_filter`; everyone else on All), so every link meant to show the whole board must be `/tasks?show=all` (Home's part links, the "All" button). Own rows carry a "Yours" tag (`task_row(..., mine=True)`), and a member's own `TaskSuggestion`s (open / added / dismissed, shown as Waiting for a lead / Added / Not now) are listed under "Your suggestions" whatever the filter. `src/progress.py`: the one place build progress is computed from `Task.status` (four parts of Crush: Enclosure incl. Electronics Mounts, Seals, Thrusters, Actuators = Gripper + Torpedo; the render-tag positions live there too)
- `src/steps.py`: the step lists per type, where a task is in them, and the lead's step editor logic (pure). `Task.stage` is the name of the current step and the status always agrees with it (todo/in_progress on a working step, needs_review on a review step, done past the last); `current_index` enforces that when reading. `Task.steps` is a lead's own list (`None` = the type's defaults). `src/shell.py`: the Jinja environment every page uses; it adds the Needs-you count (leads only) shown on the sidebar's Inbox link and the open-task count shown on its Tasks link.
- `src/workflow.py`: the task flow `todo → in_progress → needs_review → done`. **Leads are not gates**: the owner (or any lead) moves the task through every stage, a "Lead review" / "Lead approval" stage included, because the member and the lead usually talk in person. The task page and Home's Active task panel show one main button at a time: **Start → Move to next stage** (**Finish task** on the last stage), plus Unclaim, for the owner or a lead. The actions are `start`, `advance` (from `in_progress` *and* `needs_review`) and `unclaim`; there is no approve or accept any more (old `approve` / `self_approve` rows still read as "approved" in History, `taskpage.event_text`). `advance` moves one stage, sets `needs_review` when it lands on a review stage and moves on from it with the same button; moving on from a review stage reads "moved on from “Lead review”" in History, never "approved". After `advance` the next full page shows a one-time toast (`workflow.TOAST_KEY` in the session, taken by `shell.take_toast`, rendered by `base.html`: "M06 moved to “Lead review”." with a **Write today's entry** link that opens the Notebook on the task for its owner); nothing opens the Notebook by itself. Leads also change a task's type (`/tasks/{code}/type`) and edit its steps (`/tasks/{code}/steps`, htmx fragment `_steps_editor.html`; the step the task is on can't be removed or have its review setting changed). Every move is written to `TaskEvent` with a `kind` and `detail` (shown as History). `src/taskpage.py`: stage strip, History, the stored "Next step:" line Home shows (read from the latest coach answer, never a model call), and how a coach message splits into body / conflict / next step
- `docs/design.md`: the design rules ("Polar": navy instrument panels on a pale page, one orange accent, 4px corners, optional CSS-only motion); `docs/concepts/polar.html` and `polar.css` with the four `polar-*.png` screenshots are the source of truth (the older `docs/concepts/*.html` are the Drafting design it replaced). `docs/theme.md`: tokens, dark mode, motion. `src/static/styles/tokens.css` (light tokens), `theme.css` (dark tokens, the shell, Home) and `app.css` (the components) are the Polar baseline, merged by the Polar redesign PR (which lifted the old "designer's files" note): change them with the same care as any code, and keep to the rules in `docs/design.md`. `src/static/styles/extras.css` holds the few rules they don't have (form controls, notices, import table, `[hidden]`, grids that shrink on phones); add to it only when a class from `app.css` can't do the job. `src/templates/components/`: Jinja macros (status mark, task row, decision row, progress ruler, notices, empty/error states, buttons, readout, coach message). Reuse them before adding markup. `tests/test_design_tokens.py` fails on raw hex, one-off sizes or a `border-radius` other than `var(--radius)` in `extras.css`, and on any text/background pair below 4.5:1 in light or dark
- `src/scripts/screenshots.py`: what `make screenshots` runs; `requirements-dev.txt`: dev-only tools (Playwright), not in the Docker image
- `src/coach.py`, `src/templates/task.html`: the `/tasks/{code}` page and its coach chat. `converse()` is one message start to finish: save the member's message, retrieve (no model call), one streamed model call, save the answer and the `LlmCall` row. `POST /tasks/{code}/coach/stream` sends it to `coach.js` as one JSON object per line (`step`, `text` already rendered as safe HTML, `reset`, then `done`, `failed` or `rejected`); `POST /tasks/{code}/coach` is the same without streaming (no JavaScript, or htmx). A failure after the message is saved becomes a `CoachMessage` with role `error` (meta `retry_of` = the member's message id) so it survives a reload; the Retry form posts `retry=<id>` and answers that same message (no second copy, no extra use of the daily cap). Failed messages are left out of what the model is shown. `src/static/htmx.min.js` is vendored, v2.0.7, no CDN. Its only ties to the UI code are two presentation hooks, the `message_parts` filter and `taskpage.page_context(...)` in `_render_page`; the status buttons post to `workflow.py`
- `src/retrieval.py`: what the coach is told, with no model call: the Drive index searched with the question (the task title and subsystem only boost the ranking, `drive_index.search(boost=...)`, so a long title can't drown the question), (a vague question like "How do I start?" searches the title and subsystem like the question itself), top 8 chunks, max 2 per file, each cut to ~150 words in one or two windows around the matching words; the newest matching CAD file names, only when the question is about files (`wants_cad`); the section/tab headings of the top 3 files (an outline built from the index, so "what else is in this doc?" works); for a question about a quantity (clearance, thickness, size...) the 3 best matching sheet rows with their tab names; the subsystem's confirmed decisions (they outrank Drive text), every team fact, and the sources cited earlier in the thread (saved in each answer's `meta` with their file and chunk ids, so a follow-up keeps them). `IndexEmpty` when nothing has been synced. `src/answering.py`: builds the prompt, runs `llm.CoachStream`, removes Drive links the model was not given, turns a bare `[S3]` citation (smaller models cite by number) into the `[Title](link)` of that passage, flags machining numbers without a source; the pure part used by the web page, `ask_coach.py` and `make eval`
- `src/llm.py`, `src/prompts/coach_system.md`: model client and the one streamed call (`CoachStream`); its only tool is `read_file(file_id)`, one live read of a Google Doc that retrieval showed it, for when the chunks clearly don't cover the question (recommendation mode adds more tools, see `recommend.py`). 25 s hard limit for the whole answer, then it answers with what it has (or "Took too long" if there is nothing). The prompt: answer first in 1-3 sentences, sources as links, "Next step:" last; never ask which season or vehicle (team facts); a `Likely current:` paragraph when sources conflict (the page styles it); 3 short examples. Cost comes from the proxy's header, or is estimated from tokens (`ESTIMATED_PRICES`, `CallRecord.cost_estimated`) because a streamed response's headers are sent before its cost is known. Every call row (`LlmCall`) also keeps `finish_reason` (`length` = hit the output cap), `reasoning_tokens` and `tool_called`: the real reason an answer was cut off or came back empty. The output cap is `MAX_ANSWER_TOKENS` (2000; hidden thinking tokens count against it). A call with no text is `empty`: it is tried once more with `RETRY_ANSWER_TOKENS` and no tool, and if it is still empty the answer is an `empty` `LLMError`, which the page shows as a failure with a Retry button (the old "I couldn't put an answer together" text is never saved). An answer that hit the cap, or stopped at the time limit, is cut back to its last full sentence (`answering.clean_end`) and carries a "shortened" note
- `src/recommend.py`, `src/calc.py`, `src/prompts/coach_recommend.md`: recommendation mode. A **Recommend** button under the latest coach answer (`data-coach-recommend`, handled by `coach.js`; `recommend=1` on the same coach routes) sends one fixed message, "Give me your recommendation.", and the coach answers the design question discussed so far in a different shape (Recommendation / Why / Calculation / Check before you rely on it / Next step), with two extra tools on top of `read_file`: `search_references` (the Drive index's PDFs, i.e. textbooks and handbooks, plus anything under a "References" folder; every result has its link and page or section, registered as citable so the answer check keeps it, and its `[R1]` number becomes a link like `[S1]` does) and `calculate` (`calc.py`: arithmetic through `ast`, never `eval`, so the model doesn't do maths in its head). Up to 4 tool rounds and 45 s (`llm.RECOMMEND_ROUNDS`, `RECOMMEND_SECONDS`); the tools are `llm.Tool`s that `CoachStream` runs. A textbook is only searchable if it is in the index: share its folder with the service account and sync (a Drive shortcut to a folder is not followed; share the folder itself). `scripts/probe_web_search.py` tests whether Glassroom lets each model search the web (not used yet)
- `src/plan.py`, `src/prompts/coach_plan.md`: **Plan my next steps**, a button under the latest coach answer (`plan=1` on the same coach routes; message "Plan my next steps."; counts toward `COACH_DAILY_LIMIT`). One streamed call over the same retrieval with no tools and `llm.PLAN_MAX_TOKENS`, a fixed shape (What I found · What's missing · Do this now · If you need more help (a fenced prompt, shown in a box with Copy and the Drive warning) · You should end up with (no numbers: `answering` adds a note if it has digits)); `coach.with_then` adds the last part, **Then**, from `steps.then_text` (no model). `plan.parse` splits it for the page; Home's "Next step" falls back to "Do this now". An answer without the labels shows as an ordinary message. `evals/coach_questions.yaml` has `plan: true` questions (`kind: plan`)
- `src/facts.py`, `src/templates/admin_facts.html`: team facts (`TeamFact`: short sentences, all of them in every prompt), edited by leads at `/admin/facts` (add, edit, remove). Three are seeded by migration 0008
- `src/drive_index.py`: the local Drive index. `full_sync` / `incremental_sync` (Drive changes feed) read Docs (all tabs), Sheets (all tabs), PDFs (pypdf, skip over 20 MB; `DRIVE_INDEX_MAX_PDF_MB` raises it for a textbook) and CAD (name, folder and date only) into `DriveFile` / `DriveChunk` / `SyncState`; `search()` uses Postgres full text (`websearch_to_tsquery` + `ts_rank`) and falls back to LIKE on SQLite. Read-only Google scopes only. Triggers: `scripts/sync_drive.py` and the lead-only "Sync Drive now" button on `/admin`. The coach reads it through `retrieval.py`
- `src/drive_rank.py`, `src/drive_index_demote.txt`, `DRIVE_INDEX_DEMOTE`: what ranks lower in index search (folder paths with OBSOLETE, Old, Archive, Alfie, "for Comparison"; seasons more than a year behind), config next to the exclude rules. `drive_index.hit_for_model()` is the result shape for the model (folder path and modified date always present, `possibly_old` and why)
- `src/drive_exclude.py`, `src/drive_index_exclude.txt`, `DRIVE_INDEX_EXCLUDE`: the exclude rules for the Drive index (folders, `file:` names, `mime:` types), config not code. One rule is always on: the Crush document (`DECISIONS_DOC_ID`) is never indexed, so what the app writes there can't come back as new Drive evidence against the record it came from (set `DECISIONS_DOC_ID` on the sync cron service too)
- `src/markup.py`: coach answers are Markdown, rendered by markdown-it-py (raw HTML off) then sanitized with nh3 (allowlist; only https Google Docs/Drive links stay clickable). Model output is untrusted: never put it in a template unescaped except through `render_markdown` (the `markdown` filter)
- `evals/coach_questions.yaml`, `src/coach_eval.py`, `src/scripts/run_evals.py`: the coach's test questions, the scoring and report code (pure, unit-tested), and the `make eval` runner
- `src/timeline.py`, `src/templates/timeline.html`, `src/static/timeline.js`: the Timeline (`/timeline`, read-only; signed-out visitors get `auth.locked_page`). Bars come from `TaskEvent` only, through one pure function `span_for(status, moments, today)` (latest "start" event to the "done" event; a task on a review stage ends the day it moved onto it; notifications (`review_requested`, `review_seen`) are not moves and draw nothing; open runs to today; todo or no events = no bar, named at the panel's foot); `axis_for` builds whole-week columns from a Monday. Spec: `docs/timeline.md`; styles: `static/styles/timeline.css` (the designer's, loaded after `theme.css`; the few additions are in `extras.css`). On phones `timeline.js` scrolls the chart to today
- `src/profiles.py`, `src/templates/profile.html`, `components/icons.html`: member icons. `/profile` (signed in) saves a `MemberProfile` (email, icon, display_name, `full_name` = the Google name tasks' `owner` holds) for the signed-in member only; icon must be one of `profiles.ICONS` (nine), name at most 20 characters. `profiles.Profiles` turns a task's owner into chips (first name and gear until they pick); chips show on task rows, the task page, the top bar and the Timeline. The sprite of the nine drawings is `icons.avatar_sprite()` in `base.html`
- `src/inbox.py`, `src/templates/components/needs_you.html`: a lead's **Inbox** tab (`/inbox`, leads only; the list is titled "Needs you"), the only place a lead acts (count on the Inbox link in the sidebar). Three card kinds: *Work to check* (a member **notified** a lead, see `review.py` below: member, task, stage, their message, how long ago, links to the task and to the linked entry; **Seen** posts `/inbox/review/{id}/seen` and removes the card, **Send back** posts `/inbox/review/{id}/send-back` with a required one-line reason; a task that merely sits on a review stage has no card), *Answer to settle* (`AnswerRequest`; made when a member presses "Ask a lead to settle this" on a coach answer whose sources conflict or that cites nothing: `coach.ask_a_lead`, one `llm.settle_options` call lists the options, and if it fails the request is still made; a lead records an option, another value or typed text; "Not now" moves it to the end) and *New task* (`TaskSuggestion` from the member's "Suggest a task" form on /tasks; add, edit or dismiss). Any lead can act; members get 403 on every route. `src/prompts/settle_options.md` is the prompt
- `src/review.py`: **Notify a lead** and what the lead does with it. No table and no migration: everything is `TaskEvent` rows. In the Notebook's Today's entry tab, next to "Publish to Crush doc", a blue secondary **Notify team lead for review** button (`.btn--notify`, `/notebook/entry/notify`, `notebook.notify_form`), whenever the entry has a task. The side panel has no message box and shows no notice for it: pressing the button records the notification at once and a **pop-up in the middle of the screen** (`_notify_modal.html` / `_notify_card.html`, a `<dialog>` in base.html's `#notify-slot`, never inside the Notebook panel; an htmx response sends it out of band, a plain post renders it open) says "Your team lead has been notified" and asks "Do you want to add a message for them?" with a text box (280 characters, `POST /notebook/notify/{event_id}/message` → `review.add_message`, owner or lead, only while unanswered; then "Message sent"), an X, and a subtle bar at its foot that runs down over 10 seconds (3 after a message is sent) and closes it (`notebook.js`: a Web Animation, so reduced-motion doesn't stop the timer; it pauses while the member is in the text box; X, Esc and a click outside close it at once; without JavaScript it stays until the X). Blurred page behind it. It does not publish and publishing does not notify. It writes a `review_requested` event (`detail` = the message once added; `note` = JSON `{"stage", "entry"}`, read with `review.meta`; the status is not touched). While one is unanswered, pressing again adds no event and the pop-up says "Your team lead was already notified at 4:10 pm" and still lets the member add or change the message; at most 3 new notifications a day per task (`DAILY_LIMIT`, local day, checked in `review.notify`, error 429; `follow_up=1` on the entry route still makes another event but the page doesn't offer it). The entry linked is the saved draft being written, else the entry it follows up, else the member's latest published entry on the task today, else the task only; a draft's link is never shown to a lead (drafts are private), the card names it as still a draft. A notification is **unanswered** until a later `review_seen`, `send_back` (or an old `approve` / `self_approve`) event on the task; `unanswered_by_task` is the one query behind the Inbox cards (one per task, follow-ups add lines), the sidebar count and Home's "Your tasks in review" tile ("Waiting for a lead to see": tasks the member owns with an unanswered notification, not every task on a review stage). `send_back` records `send_back` with the reason in `note`; if the task is still on or past the review stage (`send_back_target`: the review stage on or before the stage the member notified from, else the next one ahead) it moves to the working stage just before it, otherwise it stays and only the reason is recorded; the member sees "Sent back: <reason>" on Home's Active task panel and the task page (`sent_back_notice`) until they move the task on, start it or notify again. Only leads (`LeadUser`, plus a check in `review.py`) can answer; members get 403. A lead may notify themselves.
- `src/decisions.py`, `src/record.py`, `src/templates/record.html`: recorded answers and the **Team record** page (`/record`; the page title, sidebar label and Home button say "Team record", the code and URL keep "record"; by part of Crush, grouped by local date, search; work notes appear as Notes behind the "Show work notes" toggle, hidden until notes exist; each entry says whether it reached the Crush document). The table keeps its names (`Decision`: proposed/confirmed/superseded); the words are Suggested / Recorded / Replaced (`models.DECISION_STATUS_LABELS`). ## Preview environments
To sign in on a Railway PR environment without Google OAuth, set two variables on **that PR environment only** (never on `production`): `DEV_LOGIN=1` and `DEV_LOGIN_TOKEN=<a long random secret>` (e.g. `python -c "import secrets; print(secrets.token_urlsafe(32))"`). Then open `https://<pr-url>/dev-login?token=<token>&as=member` (or `as=lead` for the Inbox, Admin and Record controls). `RAILWAY_ENVIRONMENT_NAME` is set by Railway itself; production is refused by name, and an environment without that name is refused too. Remove the two variables, or close the PR, to turn it off.
- This repo and its preview URLs are public, so **a preview database must hold only sample data**: use `sample_data/tasks.csv` (`python -m import_tasks`), never a real tracker export or a copy of the production database, and don't point a preview at the real Crush document (`DECISIONS_DOC_ID`) or a synced real Drive index. Treat the token as a credential: anyone who has it is a lead on that preview. It is also in the browser's history and Railway's request logs, so use a different token per environment and don't paste the link in public places.

## Rules
- Secrets live only in the environment: `GLASSROOM_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS` (path to a key file outside the repo) or `GOOGLE_SERVICE_ACCOUNT_JSON` (file contents, on Railway), `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `SESSION_SECRET`, and `DATABASE_URL`. Never write a secret into a committed file, a log line, or a test.
- The Google credential variable names are listed in `.env.example`; values stay in the local environment or Railway. Drive access is limited to files and folders shared with the service account.
- This repo is public. Never commit people's names, contact info, or exports of the tracker or Drive. Drive file names, catalog part numbers, and individual design values in eval questions are OK. Tests and seed data use made-up tasks and people.
- One task, one branch, one PR. Small commits. Never push to `main`; everything reaches `main` through a PR Samara reviews.
- Every model change needs a new Alembic migration. Never edit a migration that has been merged; add a new one. `tests/test_migrations.py` fails if the models and migrations disagree.
- Two open PRs must not both add a migration with the same number: when one merges, the other renumbers (new file, new revision id, `down_revision` = the merged head) before it merges. `test_there_is_exactly_one_migration_head` enforces this. The `.claude/hooks/` guard also blocks edits to any migration already on `origin/main` (run `git fetch origin` first so it's current).
- Every LLM or Google call handles failure: the page says plainly what failed, and the rest of the page still works.
- Log every model call (model, input and output tokens, cost, task, member) to the database; this feeds the cost-benefit analysis.
- Pages must be semantic, accessible, honest about network errors, and usable at phone width (Lab 6 standard).
- Design: follow `docs/design.md`; where CLAUDE.md or a PR says a rule changed, the newest merged PR wins.
- UI PRs attach before/after screenshots at 1280 and 375 (`make screenshots`).
- A PR that changes anything under `src/prompts`, `src/coach*.py`, `src/retrieval.py`, `src/answering.py` or `src/llm.py` puts the `make eval` summary line (before and after) in its description; the PR template has the checkbox.

## Product rules the code must enforce
- The coach advises; it never decides. Leads review in person; the app notifies them, it never waits for them. Nothing in the app waits on a lead for a task to move: members move their own tasks through every stage, and the app only lets a member optionally notify a lead (with a message) and shows the lead what to look at. Leads still record answers (Answers need a lead; notebook entries and task moves don't).
- The coach never states machining numbers (feeds, speeds, tap sizes, tolerances) without citing a source the member can open.
- Confirmed decisions in the database outrank Drive search results. If a Drive doc conflicts with a confirmed decision, flag it as possibly stale.
- Drive write-back is append-only: add a dated entry to the Crush document (`DECISIONS_DOC_ID`) under the subsystem's tab and that day's date heading, only through `src/drive_write.py`. A notebook entry is written when its member publishes it (no lead approval; drafts and private notes are never written); a recorded answer is written when a lead records it. Never edit or delete existing Drive content. The Drive sync never indexes that document.
- Drive API calls on the team folder need `supportsAllDrives=True` and `includeItemsFromAllDrives=True` (it's a shared drive).
- No XP or points. Progress is shown as Crush's build progress and each member's completed tasks.

## Measuring the coach
- Run `make eval` before and after any coach change (`src/llm.py`, `src/prompts/coach_system.md`, `src/coach.py`, `src/retrieval.py`, `src/answering.py`) and paste both summary lines in the PR description, e.g. `pass 11 / partial 3 / fail 2 | median 14.2s, max 31.0s | total cost $0.2210, $0.0147/question | tokens per question 4,850 in / 410 out`. The table also shows tokens in and out per question, and the report lists each model call's finish reason. A change that makes the numbers worse needs a reason.
- It asks every question in `evals/coach_questions.yaml` the way the task page does (`coach.task_context` + `retrieval.retrieve` + `answering.AnswerRun`, empty chat history, except a question with `after: <id>`, a follow-up, which is asked in the same chat after that question and its answer) using the real model and the local Drive index. Needs `GLASSROOM_API_KEY` and a `DATABASE_URL` whose index is synced (the Google credentials only matter for the rare live read); it refuses to start without them. A task code that isn't in the local database gets a made-up task, so answers can differ a little from the live page.
- Scoring (case-insensitive substring matches): **pass** = every `expect` appears, `cite` is the title of a source the answer links, no `must_not`; **partial** = at least half of `expect` and no `must_not`; **fail** = anything else, or an error/timeout.
- An `expect` item can be a list of alternatives (any one counts), for answers that can be worded several ways: `expect: [["not decided", "no decision"]]`.
- It waits 3 seconds between questions. A question that errors (rate limit, timeout, model error) is retried once after 20 seconds and the retry's cost counts. Errors still score as fail, but the summary line says how many fails were errors (`fail 5 (2 errors)`), and the report shows the server's log line for each, so provider flakiness isn't mistaken for a worse coach.
- It stops once the total cost passes $0.60 and says so (remaining questions show "not run"; also stops if Glassroom reports the budget is used up). `make eval RESUME=1` then keeps the last report's answers and asks only the "not run" ones (same model required; a question edited since is asked again) and writes a merged report. The Glassroom cap is $1 per 5 hours for everyone, so don't run it twice in a row on the full set. Use `ONLY=<id>` or `KIND=<kind>` while iterating. `MODEL=<name>` runs one model for this run only (`COACH_MODEL` is untouched); compare `claude-sonnet-5`, `claude-haiku-4-5` and `gemini-3.5-flash-lite` by the cost per question in the summary line (estimated prices: `llm.ESTIMATED_PRICES`).
- Every answer is written to `.context/evals/<timestamp>.md` (to read) and `.json` (to compare runs); `.context/` is gitignored. Read the failing answers before changing anything: a wrong `expect` line is as likely as a wrong answer.
